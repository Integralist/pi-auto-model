# Use Pi native virtual models for dispatch ownership

Pi's native virtual model owns physical dispatch, branch-persisted route state,
and routed context limits. Keep task-tier policy in a small extension so
portable skill metadata and bounded classification can select physical pairs
without building another provider, session harness, or routing service.

## Considered Options

1. Native virtual routing: keeps selection distinct from physical dispatch and
   preserves public assistant metadata for independently installable plugins.
2. Input-hook physical switching: avoids virtual selections, but makes policy
   mutate session settings and own more restoration/override bookkeeping.
3. A separate classifier-first router: adds another runtime even though native
   routing already supports asynchronous metadata-first policy.

## Consequences

Existing plugins need generic virtual-model support, tested without this
router. Their independence is a release gate; the accepted unused intercom
handover limitation is not. Physical model changes may lose prompt-cache reuse,
so active tasks and retries retain their chosen physical pair.

Classification adds cost, latency, and possible misclassification. Valid
metadata avoids it; bounded classification failure retains the current pair.
The four portable tiers initially share two Pi pairs. Tier step-down is a
pre-dispatch availability policy, not runtime quota or entitlement switching.
